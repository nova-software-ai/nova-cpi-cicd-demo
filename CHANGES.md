# Weather_Data_v2 — changes vs. Weather_Data

`Weather_Data_v2` is a copy of `Weather_Data` (package `WeatherData`) with five improvements.
The original `Weather_Data` was not modified, redeployed or called.

| # | Area | Before (Weather_Data 1.0.0) | After (Weather_Data_v2) | Why it is better |
|---|---|---|---|---|
| 1 | Endpoint configuration | Both Open-Meteo URLs hard-coded in the HTTP receiver channels; timeout hard-coded at 60000 ms. Only externalized parameter: `SAP_ProfileId`. | `{{GEOCODING_URL}}`, `{{FORECAST_URL}}`, `{{HTTP_TIMEOUT_MS}}`, `{{LOG_PAYLOADS}}` externalized (`parameters.prop`/`.propdef`). | The same artifact moves DEV→QA→PROD (or to a mock / proxy URL) by configuration only, without editing the model. That is also what makes the 502 test possible without changing code. |
| 2 | Forecast query builder | The query string (`latitude…&current=…&timezone=auto` + imperial units) was built twice: in `PrepareRequest.groovy` (class `WeatherQuery`) for the coordinates route, and copied inline in `SetCoordinates.groovy` for the city route. | One new step, **Build forecast query** (`BuildForecastQuery.groovy`). Both gateway routes converge on it. `PrepareRequest` and `SetCoordinates` only set `latitude`/`longitude`. | One place to change fields or units. The copies can no longer drift apart (a classic bug source). Each script does one thing, and the step name shows in the MPL. |
| 3 | Response mapping | `BuildResponse.groovy` mapped JSON→JSON in code. | **Forecast JSON to XML** (converter) → **Map to WeatherReport** (XSLT `WeatherReport.xsl`) → **WeatherReport XML to JSON** (converter) → **Set response headers** (Content Modifier). | The output contract is a declarative, reviewable artifact. It's visible as a mapping step in monitoring and is standard CPI tooling. Location data arrives as XSLT parameters from exchange properties. |
| 4 | Error handling | `returnExceptionToSender=true`, no exception subprocess: callers got raw exception text with HTTP 500, and the MPL had no root cause beyond the stack. | **Exception Subprocess** → `BuildErrorResponse.groovy`: `{"error":{code,status,message,messageProcessingLogId}}` with 400 `INVALID_REQUEST`, 404 `CITY_NOT_FOUND`, 502 `UPSTREAM_ERROR`, 500 `INTERNAL_ERROR`. It logs the root cause (exception chain, failed step, downstream status/body) as the MPL attachment `Error detail` and custom header properties. `returnExceptionToSender=false`. | Callers get a stable contract and the right status codes. No internal stack traces leak out. Support starts from the MPL ID in the response and finds the root cause in one place. |
| 5 | Payload logging | None (0 MPL attachments). | `PayloadLogger.groovy` (one script, three functions: `logRequest`, `logDownstream`, `logOutput`) attaches `01 Request in`, `02 Downstream response - Geocoding/Forecast`, `03 Final output`. It's switched by `{{LOG_PAYLOADS}}`. | Payloads are visible without Trace level (which expires after 10 minutes and needs a UI role), and can be switched off in production by configuration. |

Sender endpoint: `/http/weather-v2` (the original keeps `/http/weather`).
